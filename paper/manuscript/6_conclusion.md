# 6 Conclusion

This paper asked whether the numbers routinely used to compare object detectors, theoretical FLOPs and vendor latency, tell a practitioner how fast a model will actually run on a CPU. The measured answer, on one CPU under two named protocols, is that FLOPs do not, and that the discrepancy is systematic rather than incidental.

The conclusions that follow are an abstraction of the measured table, not a restatement of it. Putting that measurement behind cross-family comparison lets us quantify, on this hardware class, what prior work stated qualitatively: theoretical FLOPs overstate CPU speed advantages by an amount that grows with the scale gap, reaching about 1.3× for the closest pair and about 2.0× for the widest pair under either protocol, because CPU inference time is governed by memory traffic, kernel efficiency, and post-processing, none of which an arithmetic count can capture. Efficiency is a property of the whole runtime stack rather than of a model or family alone, as shown by a same-ISA, cross-environment forward-only check on the same CNN models (reported as rank-only evidence rather than pooled with the local measurements) and by a matched-accuracy pair in which a Transformer detector measured faster than its CNN counterpart on this CPU. LAE is retained as a descriptive joint-cost sensitivity analysis; deployment recommendations use explicit budget filtering and application priorities rather than claiming a superior index.

**Implications.** For efficiency reporting, a model card listing FLOPs and parameters without measured CPU latency under a named warm-up protocol cannot support cross-family or cross-platform claims. Cross-round medians test stability across independently sampled windows, while a single contiguous window places every model in one pass under comparable conditions. For model selection, report the feasible set under explicit accuracy, latency-tail, and parameter budgets, then apply the deployment priority. For a practitioner considering INT8 on a CPU, quantization is a size lever and can be an accuracy lever when the detection head is preserved, but it is not an automatic speed lever. In these experiments, QDQ and QOperator paths showed different outcomes under ONNX Runtime; because activation types were not fully matched, the result is toolchain-specific evidence, not proof that format alone determines speed.

**Limitations and scope.** Section 5.4 sets out the scope within which the conclusions hold and the data- and method-borne limits the study carries inside it. In brief, they are evidence about how to benchmark a detector on a CPU and are bounded by one runtime on one CPU class, by vendor-supplied accuracy references rather than recomputed ones, and by a seven-model set with one instance per scale. The mechanistic account in Section 5 is interpretation built on the measured quantities, not a separately measured quantity.

**Future work.** Re-measuring the same seven-model table on further CPUs and runtimes, with the Transformer models included, would upgrade rank-only portability into transferable absolute latencies and would test whether the scale-dependent FLOPs overstatement is a property of this CPU class or of CPU execution in general. Recomputing full-validation accuracy ourselves and adding recent small variants would widen the frontier on which the index is validated. On the quantization side, profiling the dequantization and node-insertion overhead documented here, and evaluating on a CPU whose integer units are actually exercised, would separate a toolchain deficiency from a genuine ceiling of integer inference for detectors.
